# Coding Guidelines (요약)

이 스킬은 작업을 시작하기 전에 항상 읽고 따를 규약을 담고 있습니다. 핵심 파일: references/CODING_GUIDELINES.md

사용 방법

- 언제: 사용자가 "코딩해줘", "수정해줘", "PR 준비" 등 작업을 요청할 때 항상 먼저 트리거하여 요약된 체크리스트를 제공.
- 동작: 규약을 읽고 해당 작업에서 특히 주의해야 할 항목(포맷터, 브랜치 네이밍, 테스트 요구 등)을 한 문단으로 요약해 사용자에게 확인을 요청.
- 묻기: 규약에서 불명확한 부분이 있거나 선택지가 필요한 경우(예: 포맷터 설정 변경, 커밋 스타일 등) 한 가지 질문으로 묻기.

중요: 코드 주석은 한국어로 작성할 것 — 사람이 이해할 수 있도록 의도와 동작, 입력/출력, 가정사항을 한국어로 명확히 남기되 과도하게 장황하지 않게 유지합니다.

작업 기록 (Persistence)

- 모든 개발 작업과 의사결정은 리포지토리 내부 및 에이전트가 접근 가능한 메모리에 상세히 기록해야 합니다. 이는 AI 에이전트를 새로 셋업하더라도 진행 상황을 파악할 수 있게 하기 위함입니다.
- 기록 위치(권장):
  1. 리포지토리: docs/WORKLOG.md 또는 docs/progress/ YYYY-MM-DD.md 형태로 저장 (커밋과 함께).
  2. 에이전트 메모리: memory/YYYY-MM-DD.md 파일에 작업 요약과 중요한 결정/파일/브랜치/커밋 해시를 남김.
- 기록 내용(권장 형식):
  - 날짜/시간(ISO 8601)
  - 작업 요약(한두 문장)
  - 변경된 주요 파일 목록
  - 관련 커밋 해시 및 브랜치 이름
  - 중요한 결정/선택지와 이유
  - 다음 작업(간단한 TODO)
  - 테스트 및 검증 방법(로컬 명령어 포함)
- 기록은 사람이 읽기 쉽도록 간결하지만 충분히 상세하게 작성할 것. 가능한 경우 관련 커밋/PR 링크를 포함.
- 자동화: 가능한 경우 스크립트나 훅으로 WORKLOG 업데이트를 자동화(예: 커밋 메시지 템플릿, git hook)하도록 권장.

참고 자료: references/CODING_GUIDELINES.md

SKILL.md 변경 및 푸시

- SKILL.md는 이 스킬의 핵심 문서입니다. SKILL.md를 수정하면 반드시 리포지토리에 커밋하고 원격(origin)에 푸시해야 합니다. 이는 다른 에이전트나 협업자가 최신 규약과 동작을 즉시 참조할 수 있게 하기 위함입니다.
- 권장 워크플로:
  1. 변경 후 로컬에서 내용을 검토하고 커밋 메시지에 변경 요약을 명확히 적기.
  2. git push origin <branch>로 원격에 푸시.
  3. 가능하면 변경 내용은 작은 단위로 나누고 PR을 통해 리뷰를 받기.
- 자동화 권장: SKILL.md 변경 시 자동으로 워크로그에 항목을 추가하거나(예: scripts/update_worklog.sh), CI에서 규약 검사(예: SKILL.md 형식 검사)를 실행하도록 설정할 것.

배포 전 검증 및 푸시 규칙 (핵심 변경사항)

- 작업 완료 후 반드시 로컬에서 빌드/린트/테스트를 실행하여 에러가 없는 것을 확인한 뒤에 푸시합니다.
  - 예시 명령어(프로젝트에 맞게 조정):
    - npm run format (코드 포맷 적용)
    - npm run lint (린팅)
    - npm run lint:fix (자동 수정)
    - npm test (테스트 실행)
    - (Godot) 에디터에서 씬 로드/스크립트 오류 확인 또는 export 테스트
- 에러가 발생하면 에러를 해결할 때까지 수정 → 재검증(빌드/린트/테스트)을 반복합니다. 에러가 완전히 해결되면 커밋하고 푸시합니다.
- 기본 동작: 소스코드 수정 작업이 끝난 뒤 보고하기 전에 반드시 원격에 푸시합니다(보고 전 푸시가 기본). 이는 원격에서 CI/협업자가 변경을 즉시 검증할 수 있게 하기 위함입니다.
- WORKLOG 업데이트: 중요한 변경(특히 SKILL 관련/아키텍처 변경)은 푸시와 함께 WORKLOG에 요약을 남기고 커밋 해시를 포함합니다. (자동화 스크립트가 있으면 사용)
- 예외 및 주의사항:
  - 긴급 핫픽스나 보안 패치의 경우, 우선 로컬에서 빠르게 검증 후 푸시하되 PR/리뷰 절차는 가능한 한 빠르게 진행합니다.
  - 대규모 변경은 작은 단위로 나누어 단위 검증 후 푸시하는 것을 권장합니다.
